# BE-10 — External Notification Connectors: Implementation Plan

> **Status:** ready to implement (nothing built yet). **Design source:** [`docs/NOTIFICATION_CONNECTORS.md`](../NOTIFICATION_CONNECTORS.md) (authoritative design) and the epic entry in [`docs/IMPLEMENTATION_TASKS.md`](../IMPLEMENTATION_TASKS.md) (BE-10.1–BE-10.5).
>
> **How to use this file (implementing agent):** implement one phase at a time — **one phase = one branch (`be-10.<n>-…` via git worktree) = one PR** containing backend + frontend + tests + the `docs/IMPLEMENTATION_TASKS.md` update. All open design questions are already resolved in §1 below — do not re-litigate them. Follow the per-phase Definition of Done and the project's `CLAUDE.md` pre-push checklist. Line-number references were verified against `main` at the time of writing; re-verify anchors (especially the next free migration number) before editing.

**Scope:** Phases 1–4 of `docs/NOTIFICATION_CONNECTORS.md`. Phase 5 (per-user relay) is explicitly **out of scope** — but `Announcement.Event` stays a string field so event kinds can widen later without redesign.

**Ground rules (from the design doc, non-negotiable):**
- One canonical `TorrentPublished` event, emitted at exactly two points; connectors never hook moderation internals.
- Compile-time connector registry — no hot-loading, no plugin framework.
- Secrets: plaintext in DB, but **marked** per kind, **never** returned by the API, **never** logged (including delivery-log `last_error`).
- Anonymous uploader identity must never appear in any event payload, announcement, delivery row, or connector output.
- Each phase = one PR containing BE + FE + tests + `docs/IMPLEMENTATION_TASKS.md` update.

**Delivery data flow (all phases):**

```
ApproveTorrent / Upload(auto-approve)
  └─ publishPublished() ──> event bus (synchronous)
       └─ ConnectorDispatcher listener (own 5s ctx, like listener/notification.go)
            ├─ kill-switch check (site setting connectors_enabled)
            ├─ build Announcement (anonymous-safe)
            ├─ for each enabled instance where Filters.Matches:
            │    INSERT connector_deliveries (ON CONFLICT (instance_id,event_key) DO NOTHING)  ← dedupe
            │    if inserted → enqueue asynq "connector:drain" {instance_id} (Unique 5s)       ← burst collapse
            └─ never delivers inline
asynq drain handler (per instance)
  ├─ budget = rate_per_min − CountSentSince(instance, now−60s)
  ├─ ListDue(pending, next_attempt_at <= now, ordered)
  ├─ deliver each with recover() + 10s ctx; success → MarkSent
  ├─ budget exhausted with >1 left → deliver ONE coalesced "+N more" line, mark rows 'coalesced'
  └─ failure → attempts++, next_attempt_at = backoff, re-enqueue drain ProcessIn(backoff); attempts>5 → 'failed'
```

## 1. Resolved design decisions (do not re-litigate during implementation)

1. **Chat system messages** — migration makes `chat_messages.user_id` nullable and adds `system BOOLEAN NOT NULL DEFAULT FALSE`; `model.ChatMessage` keeps `UserID int64` (repo maps NULL↔0) and gains `System bool`; new `ChatService.SendSystemMessage(ctx, message)` skips mute/privilege checks and sets `Username: "System"`. *Why:* a fake "system user" row would pollute user lists, member counts, and admin search; the nullable-FK ripple is contained to the chat repo scan.
2. **WS broadcast for system messages** — add public `func (h *ChatHub) Broadcast(payload []byte)` that sends `ChatBroadcast{Data: payload}` on the existing internal `broadcast chan ChatBroadcast` (`chat_ws.go:93`); the chat connector receives it as an injected `func([]byte)`. Payload mirrors `chatMessagePayload()` (`chat_ws.go:595`) plus `"system": true`. *Why:* worker and HTTP server run in one process (`main.go` runs both), same pattern as the existing `SendToUser` bridge in `WorkerDeps`.
3. **Connector interface** — deviate slightly from the doc's `Deliver(ctx, cfg, a)`: pass the instance, because persistent connectors (IRC) must map a delivery to a *running client* by instance ID:
   ```go
   type Instance struct { ID int64; Name string; Config json.RawMessage }
   type Connector interface {
       Kind() string
       Singleton() bool                 // chat, sse = true
       SecretFields() []string          // e.g. {"hmac_secret"} — drives redaction/merge
       ValidateConfig(cfg json.RawMessage) error
       Deliver(ctx context.Context, inst Instance, a Announcement) error
   }
   type PersistentConnector interface { Connector; Start(ctx context.Context, inst Instance) error }
   ```
   Adopt this signature in Phase 1 so Phase 2 needs no interface churn.
4. **Dedupe** — `UNIQUE INDEX ON connector_deliveries(instance_id, event_key)` with `event_key = "torrent.published:<torrent_id>"`; dispatcher inserts with `ON CONFLICT DO NOTHING` and only enqueues on actual insert. Test-sends use `event_key = "test:<uuid>"` so they never conflict. *Why:* DB-enforced, race-safe across nodes and retries; check-before-send races with concurrent dispatch.
5. **Retry** — app-managed, not asynq-managed: delivery rows carry `attempts`/`next_attempt_at`; backoff `30s·2^(attempts−1)` capped at 10m; after 5 attempts → status `failed` (dead-letter, visible in admin log). The drain task itself uses `asynq.MaxRetry(0)` and returns nil on connector errors. *Why:* coalescing and dedupe need the DB view of the whole pending set; asynq per-task retry can't see siblings and would fight the unique-index dedupe.
6. **Rate-limit + coalescing** — per-instance budget from a *common* optional config key `rate_per_min` (default 20, parsed generically by the drain handler); when budget is exhausted with >1 pending, deliver one coalesced announcement (`"+N more new torrents"`, `Announcement.Event` unchanged, `Coalesced: N` field) and mark the rows `coalesced`. *Why:* the drain-per-instance model makes both trivial and keeps ordering per instance; the "leaning: coalesce" open question is hereby decided as coalesce.
7. **Test-send** — `POST /api/v1/admin/connectors/{id}/test` runs **synchronously** in the handler path: `ConnectorService.TestSend` builds a canned sample `Announcement` (fake torrent, `Event: "test"`), calls `Deliver` with a 10s timeout + recover, records a `connector_deliveries` row (`event_key "test:<uuid>"`), returns `{status:"sent"|"failed", error?}`. Bypasses filters, kill-switch and queue; **does** go through the SSRF guard. *Why:* the admin needs immediate feedback; the delivery row keeps the log complete.
8. **Write-only secrets** — GET responses strip secret keys from `config` entirely and add `"secrets_set": ["hmac_secret", ...]`. On update, `MergeSecrets(existing, incoming, secretFields)`: secret key **absent or empty string** → keep stored value; **non-empty** → replace; **explicit JSON `null`** → clear. Validation runs on the *merged* config. *Why:* "leave blank to keep" is the standard UX; explicit null gives a clear-path without a second endpoint.
9. **SSRF guard** (`connector/httpguard`) — `httpguard.NewClient(allowPrivate bool)` returns an `*http.Client` whose `net.Dialer.Control` callback rejects, **at dial time on the actual IP**: loopback, RFC1918, link-local (incl. `169.254.169.254`), CGNAT `100.64/10`, unspecified, multicast, and IPv6 equivalents (`::1`, `fe80::/10`, `fc00::/7`); scheme must be http/https; `CheckRedirect` caps at 3 (redirect targets re-enter the same dialer, so they're covered). Escape hatch: site setting `connectors_allow_private_networks` (default `false`) for homelab receivers. *Why:* Control-time checking defeats DNS rebinding and redirect tricks in one place; a single global knob is enough for a self-hosted tracker.
10. **Retention** — site setting `connector_delivery_retention_days` (default 30); pruned in the existing `NewMaintenanceHandler` step list via `ConnectorDeliveryRepo.DeleteOld(cutoff)`, guarded like `NotificationRetention` (non-positive disables). The maintenance job **also** re-enqueues drains for instances with due pending rows (`InstancesWithDue`) — the crash-recovery safety net.
11. **Activity log** — `TorrentPublished` is **not** subscribed by `RegisterActivityLogListeners` and gets no `IsStaffOnly` entry. *Why:* the activity log already records `torrent_uploaded` and `torrent_moderated` for the same transitions; a third row per publish is pure noise, and keeping the event out of the log means its payload is never serialized into `activity_logs.metadata` at all (defense-in-depth for the anonymous flag).
12. **Anonymous safety at the source** — `TorrentPublishedEvent.UploaderName` is `""` whenever `Anonymous=true` (the service never copies the real name into the event). Renderers print "Anonymous". *Why:* redact at the earliest point so no downstream consumer can leak it.
13. **IRC library** — `github.com/ergochat/irc-go` (`ircevent` + `ircmsg`). *Why:* actively maintained by the Ergo IRCd team, built-in reconnect loop and SASL support (both explicitly required), ISC-licensed; `girc` is fine too but has no built-in reconnection, which we'd have to hand-roll.
14. **Leader election** — Postgres advisory lock (per the doc's "leaning"): dedicated `*sql.Conn`, `SELECT pg_try_advisory_lock($1,$2)` with two int4 keys `(0x636F6E6E /* "conn" */, instance_id)`; never explicitly unlocked — session end releases. Ownership re-check: ping the dedicated conn (`SELECT 1`, 5s timeout) every 10s; any failure → stop IRC client immediately, then re-acquire on a fresh conn with backoff. Single process acquires instantly = zero-config default.
15. **SSE** — plain `net/http` + `http.Flusher`, no library; an `AnnounceHub` modeled directly on `ChatHub` (register/unregister/broadcast channels, buffered per-client send chans, drop-slow-clients). Auth via `?token=` query param validated against the session store (EventSource cannot set headers — same reason `/ws/chat` does query-param auth). Multi-node caveat documented: fan-out reaches only clients connected to the node that ran the drain; acceptable for the single-process default, Redis pub/sub is future work.
16. **Kill-switch** — `connectors_enabled` site setting (default `true`) checked once in the dispatcher; mutes **all** kinds including chat/SSE. *Why:* one predictable switch; per-instance `enabled` already provides granularity.
17. **Templates** — optional per-instance `template` config key, Go `text/template` over a fixed render context (`.Name .Category .SizeHuman .Size .URL .Uploader .Freeleech .FileCount`); parse-validated in `ValidateConfig`; per-kind default template consts in each connector package. Shared helper `connector.RenderTemplate(tmpl string, a Announcement) (string, error)`.

- Deliver via the shared `httpguard` client: POST JSON
  ```json
  { "username": "...", "avatar_url": "...",
    "embeds": [{ "title": "<name>", "url": "<torrent url>", "timestamp": "<RFC3339>",
      "description": "<template-rendered or default>",
      "fields": [{"name":"Category","value":"...","inline":true},
                 {"name":"Size","value":"...","inline":true},
                 {"name":"Uploader","value":"Anonymous|name","inline":true}] }] }
  ```
  Coalesced → plain `content: "N new torrents published — <site url>"`. Handle 429: parse `retry_after`, return a transient error (pipeline backoff handles pacing; optionally map to a reschedule like `ErrNotConnected` — keep simple: normal retry). **Error strings must not contain the webhook URL** — use `RedactError` and never wrap the URL into errors (`fmt.Errorf("discord webhook returned %d", status)`).

**T2 — Telegram connector** (`backend/internal/connector/telegram/telegram.go`):
- Config `{ "bot_token": string(secret), "chat_ids": ["-100123..."], "template"?: string }`; `SecretFields() = ["bot_token"]`. ValidateConfig: token non-empty, ≥1 chat_id.
- Deliver: for each chat_id, POST `https://api.telegram.org/bot<token>/sendMessage` with `{"chat_id":..., "text": rendered, "parse_mode":"HTML", "disable_web_page_preview":true}`; default template uses `<b>`/`<a href>` HTML with **all interpolated fields HTML-escaped** (torrent names contain `&`, `<` routinely — escape via `html.EscapeString` inside the render context, test it). Partial failure across chat_ids: aggregate — if any chat fails, return error (whole delivery retries; sendMessage is idempotent-enough for an announce, doc accepts harmless duplicates). **The token must never appear in errors or logs** — the request URL contains it, so error paths must not echo the URL (`fmt.Errorf("telegram sendMessage chat %s: status %d", chatID, status)`), and add a `RedactError` pass as backstop.

## 6. Cross-phase risks & pitfalls

1. **Migration numbering races** — 071 is next *today*; other stories may land first. At the start of each phase, `ls backend/migrations | tail` and take the next free number; **never renumber or edit a merged migration** (goose tracks by version; integration tests run the full chain).
2. **Hot files: `router.go`, `main.go`, `repository.go`, `deps.go`, `event.go`, `IMPLEMENTATION_TASKS.md`** — every phase touches them and so does every other worktree. Keep additions append-style in the established blocks (new nil-guarded route group; new `Deps` field at the end; new repo interfaces at the bottom) to minimize conflict surface; rebase before push.
3. **Event bus is synchronous** — the dispatcher runs inline with `ApproveTorrent`'s request. It must only do DB inserts + Redis enqueues (fast), with its own 5s timeout context, and must swallow-and-log per-instance errors so a broken connector row can never 500 an approve. Never call a connector's `Deliver` from the listener.
4. **Asynq payload stability** — drain payload is `{"instance_id":N}` and must stay backward-compatible: queued tasks survive deploys. Never add required fields; state lives in `connector_deliveries`.
5. **Config JSONB is admin input, not trusted** — always `ParseFilters`/`ValidateConfig` on read paths too (rows may predate validation changes); use `DisallowUnknownFields` for filters but be lenient reading old configs (unknown config keys tolerated on read, validated on write).
6. **Secret leakage vectors to guard in review**: `last_error`, slog calls (never log `config`), `connector_deliveries.payload`, activity log metadata (avoided by not subscribing), test-send responses, asynq task payloads, and error wrapping that embeds request URLs (Telegram token lives in the URL!).
7. **Coverage floor (80.0)** — `cmd/server` is excluded but `internal/connector/*` is not; the manager/ircevent glue is the hardest to cover — the `ircConn` interface seam and fake-lease seam exist precisely so the loops are testable. Don't ship untestable glue.
8. **Chat migration Down** must delete system rows before restoring NOT NULL, or `goose down` breaks the integration harness.
9. **testcontainers `-short` skip** — repo tests must call `requireDB(t)`; unit packages must not import testcontainers.
10. **ChatHub coupling** — worker-side chat delivery reaches WS clients only because HTTP server + worker share a process. If the deployment ever splits them, chat/SSE connectors on the worker node broadcast to nobody. Note this in code comments; it mirrors the existing `SendToUser` bridge assumption, so it's consistent — not new debt.
11. **Advisory-lock key collisions** — `(0x636F6E6E, instance_id)` uses the two-int4 form; keep the class constant unique in the codebase (grep for other advisory-lock usage first — none exists today).
12. **Bulk-approval bursts** — the `Unique(5s)` drain collapse plus rate budget handles it, but the dispatcher still does one `InsertPending` per instance per event inside the request path; with N instances that's N inserts per approve — fine for realistic N (<20), don't "optimize" with batching complexity.

## 7. Guidance for the implementing agent

- **One phase = one branch = one PR** (`be-10.<n>-…` via git worktree), BE + FE + tests + docs update together. Do not start phase N+1 in the same PR.
- **Do not** build ahead: no generic "channel abstraction" beyond the stated interfaces, no hot-loading, no per-user anything (Phase 5), no secret encryption (explicitly decided against for now — but keep `SecretFields()` accurate so it stays retrofittable), no Redis-lease leader variant, no WebSocket for the feed.
- **Do not** touch merged migrations, `TorrentModeratedEvent`, or the moderation flow beyond adding the two `publishPublished` calls.
- Resolve nothing anew: every open question in `docs/NOTIFICATION_CONNECTORS.md` §12 is decided in §1 of this plan; if reality contradicts a decision (e.g. a lib is abandoned), note it in the PR description and pick the nearest equivalent.
