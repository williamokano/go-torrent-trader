Install

Running your own tracker

One Docker stack brings up the tracker, the database, Redis and object storage. You need a machine, a domain, and about ten minutes.

Before you start

What you need

Machine Any Linux host with Docker and Docker Compose. A small VPS is enough to start — the tracker is a Go binary and the database is the part that grows.
Domain A hostname pointing at the machine. BitTorrent clients will announce to it, so it needs to be reachable from the internet.
TLS A reverse proxy terminating HTTPS. Caddy or nginx both work; see the note at the bottom.
SMTP Optional but recommended — used for email confirmation, password resets and notification digests.

Docker

The quick path

  1. Get the code

    git clone https://github.com/williamokano/go-torrent-trader.git
cd go-torrent-trader

  2. Write your configuration

    Copy the example and fill in the required values. Everything else has a sensible default. 

    cp stack.env.example stack.env
$EDITOR stack.env
    POSTGRES_PASSWORD Database password. No default — set it.
    MINIO_ROOT_PASSWORD Object storage password, minimum eight characters. Torrent files live here.
    S3_SECRET_KEY Same value as the MinIO password.
    SITE_NAME What your community is called.
    SITE_BASE_URL Your public URL. This is what ends up in announce URLs and emails, so it must be the real one.

    Generate real passwords. openssl rand -hex 32 produces something suitable. The example file ships with obvious placeholders precisely so a half-configured stack is easy to spot.

  3. Bring it up

    docker compose -f docker-compose.stack.yml up -d

    Database migrations run automatically on start, so there is no separate setup step. Watch the logs with docker compose -f docker-compose.stack.yml logs -f.

  4. Create the first account

    Register through the web interface. The first account is an ordinary member, so promote it to administrator directly in the database — this is the only step that needs psql: 

    docker compose -f docker-compose.stack.yml exec postgres \
  psql -U torrenttrader -d torrenttrader \
  -c "UPDATE users SET group_id = (SELECT id FROM groups WHERE slug = 'administrator') WHERE username = 'YOUR_USERNAME';"

    Log out and back in, and the admin panel appears.

  5. Decide who can join

    Registration is invite-only by default. Change it in Admin → Settings if you want an open sign-up, or leave it closed and hand out invites.

  6. Optional: set up the command-line tool

    Each release includes tt, a command-line tool for administering the site without a browser. Point it at your site and log in: 

    tt profile set mysite --url https://tracker.example.com
tt auth login mysite       # asks for your username and password
tt whoami

    It stores the token in credentials.yaml under your config directory, readable only by you, and refuses to use the file if that stops being true.

    The token a login returns expires after an hour, so tt also stores the refresh token that comes with it and renews the short one by itself. That means a scheduled job keeps working without anyone re-entering a password. For a script, supply the password through TT_PASSWORD or --password-stdin rather than typing it, and run tt auth logout when you are done — it ends the session on the server, not just on your disk.

    A login carries every permission your account has, which is more than a scheduled job usually needs. Scoped keys that can be granted narrowly and revoked on their own are still to be built; when they arrive, tt auth set-token already accepts one. Nothing else on the site needs any of this — it is only worth doing if you intend to script against it.

From source

Running it for development

If you want to change the code rather than just run it, the repository has a task runner that starts everything with hot reload. 

cp .env.example .env
task tools              # golangci-lint, air
task frontend:install
task dev:up             # Postgres, Redis, MinIO, Mailpit
task dev                # backend and frontend, both reloading

The frontend serves on :5173, the backend on :8080, and Mailpit catches outgoing email at :8025 so you can see confirmation messages without a real SMTP server. Full details are in DEVELOPMENT.md.

In front of it

Reverse proxy and TLS

Put a proxy in front and terminate TLS there. The backend expects to receive the real client address, so forward it — the tracker records peer IPs from the connection, and a proxy that hides them will make every peer look like it is coming from localhost. 

# Caddy — the whole file
tracker.example.com {
    reverse_proxy localhost:8080
}

Caddy sets X-Forwarded-For and obtains certificates on its own. With nginx, set proxy_set_header X-Real-IP $remote_addr; and use certbot.

Announce traffic is chatty. Every client checks in on an interval, so the tracker endpoint sees far more requests than the website does. If you put a rate limiter in your proxy, exclude /announce and /scrape or you will break swarms.

Coming from TorrentTrader 3.x

Reading your old database

If you already run a PHP TorrentTrader, the migration tool reads its MySQL database and works out where everything should go. It does not write anything yet — moving the data is still being built — but the three commands below tell you what a move would involve, which is worth knowing before you plan one.

discover Lists the tables in your old database with their row counts, so you know the size of the job. --table users prints one table's columns and the exact DDL your server reports.
validate Compares your schema against a stock TorrentTrader 3.0 and reports what differs — tables you have dropped, tables and columns your mods added, and columns whose type has changed. It also tells you what character set your text is stored in, which matters: an older install is usually latin1, the new tracker stores UTF-8, and text copied across without being converted comes out as mojibake. Differences are expected; it only fails when something the migration actually reads is genuinely missing.
mapping Writes a YAML file proposing where every one of your columns should land in the new schema, with the reasoning kept as comments next to each decision. Columns your mods added come through marked custom for you to decide on.

The mapping file is meant to be read and edited. No two TorrentTrader installs are alike after a few years of mods, so the tool reports what it found rather than assuming, and the file is yours to correct before anything is written. Keep it in version control alongside the rest of your deployment. 

task migration-tool:build

./migration-tool/migrate mapping \
  --source "mysql://user:password@your-old-host:3306/torrenttrader" \
  --out mapping.yaml

Released binaries for Linux, macOS and Windows are attached to every release if you would rather not build it. The tool only ever reads from the old database.

Passwords will not carry over yet. The tracker currently verifies only its own password format, so a hash brought across from an older install cannot be checked and the member cannot log in. Plan on everyone resetting their password after a migration until that is fixed — it is tracked as issue 228, and this page will say otherwise when it is true.

Passkeys are a different matter: those are copied exactly, so the .torrent files your members already have keep announcing and nobody has to re-download anything.

Keeping it running

Backups

The admin panel can take database backups on a schedule and download them. Back up the object storage volume too — that is where .torrent files live, and a database without them leaves every torrent undownloadable.
